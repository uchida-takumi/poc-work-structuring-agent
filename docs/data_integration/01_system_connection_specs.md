# システム連携仕様書

## 概要

本書は、サプライチェーン統合データ基盤における主要5系統（調達・生産・在庫・物流・品質）のシステム連携仕様を定義する。

---

## 1. 調達系統（ERP連携）

### 対象システム
- **ソースシステム:** SAP ERP（調達モジュール：MM/Purchasing）
- **ターゲット:** 統合データレイク（調達レイヤー）

### 連携データ

| データ種別 | テーブル/エンティティ | 主要フィールド | 連携頻度 |
|---|---|---|---|
| 購買発注（PO） | EKKO/EKPO | PO番号, 品目コード, 数量, 納期, サプライヤーコード, 単価 | 日次（差分） |
| 入庫実績 | MSEG/MKPF | 伝票番号, 品目コード, 入庫数量, 入庫日時, 拠点コード | リアルタイム（CDC） |
| サプライヤーマスタ | LFA1/LFB1 | サプライヤーコード, 名称, 与信区分, 評価スコア | 週次（全量） |
| 品目マスタ | MARA/MARC | 品目コード, 品目区分, 調達リードタイム, 安全在庫量 | 週次（全量） |
| 価格・契約情報 | A018/KONV | 品目コード, 有効期間, 価格条件, 通貨 | 日次（差分） |

### 連携方式

```
SAP ERP
  │
  ├─ CDC (Change Data Capture)   ──→ Kafka Topic: sc.procurement.goods-receipt
  │    └─ 対象: 入庫実績（MSEG）
  │
  └─ バッチ抽出（SFTP + CSV）    ──→ Data Lake: /raw/procurement/
       └─ 対象: PO, マスタデータ
```

### 技術仕様

- **CDC方式:** SAP LT Replication Server (SLT) → Apache Kafka
- **バッチ方式:** SAP Data Services → SFTP → Azure Data Lake Storage Gen2
- **データ形式:** CDC=Avro（Confluent Schema Registry管理）、バッチ=CSV（UTF-8, BOM無し）
- **認証方式:** OAuth2.0 / サービスアカウント（最小権限原則）
- **暗号化:** 転送時TLS 1.2以上、保管時AES-256

### SLA

| 指標 | 目標値 |
|---|---|
| CDC遅延（入庫実績） | ≦5分 |
| バッチ処理完了時刻 | 翌営業日 07:00 JST |
| データ可用性 | 99.5%/月 |
| 障害通知 | 30分以内アラート |

## 2. 生産系統（MES連携）

### 対象システム
- **ソースシステム:** 製造実行システム（MES）/ ライン制御システム
- **ターゲット:** 統合データレイク（生産レイヤー）

### 連携データ

| データ種別 | 主要フィールド | 連携頻度 |
|---|---|---|
| 製造指示（Work Order） | WO番号, 品目コード, 計画数量, 計画開始/終了日時, 工程コード, 拠点コード | リアルタイム（CDC） |
| 実績（生産実績） | WO番号, 実績数量, 良品数, 不良数, 実績時間, 停止時間 | リアルタイム（CDC） |
| 設備稼働データ | 設備ID, 稼働状態, 電流値, 温度, 回転数, タイムスタンプ | リアルタイム（IoT） |
| 工程マスタ | 工程コード, 工程名, 標準サイクルタイム, 能力（本/時） | 週次（全量） |
| BOM（部品表） | 親品目コード, 子品目コード, 所要数量, 有効日 | 週次（全量） |

### 連携方式

```
MES / ライン制御
  │
  ├─ OPC-UA / MQTT  ──→ IoT Hub  ──→ Kafka Topic: sc.production.equipment-telemetry
  │    └─ 設備テレメトリ（1秒間隔）
  │
  ├─ REST API（Push）  ──→ Kafka Topic: sc.production.work-order
  │    └─ WO作成/更新イベント
  │
  └─ DB直接抽出（JDBC）  ──→ Data Lake: /raw/production/
       └─ マスタデータ、実績集計（日次バッチ）
```

### 技術仕様

- **IoT連携:** Azure IoT Hub → Stream Analytics → Kafka
- **イベント連携:** MES REST API Webhook → Kafka Connect HTTP Source Connector
- **データ形式:** テレメトリ=JSON、イベント=Avro、バッチ=Parquet
- **スキーマ管理:** Confluent Schema Registry（backward互換性必須）

### SLA

| 指標 | 目標値 |
|---|---|
| 設備テレメトリ遅延 | ≦30秒 |
| WOイベント遅延 | ≦2分 |
| バッチ処理完了時刻 | 当日 23:00 JST |
| データ可用性 | 99.0%/月 |

## 3. 在庫系統（WMS連携）

### 対象システム
- **ソースシステム:** 倉庫管理システム（WMS）
- **ターゲット:** 統合データレイク（在庫レイヤー）

### 連携データ

| データ種別 | 主要フィールド | 連携頻度 |
|---|---|---|
| 在庫残高スナップショット | 品目コード, 拠点コード, ロケーション, 在庫数量, 在庫金額, 基準日 | 日次（全量） |
| 在庫移動トランザクション | 移動番号, 品目コード, 移動元/先拠点, 移動数量, 移動日時, 移動区分 | リアルタイム（CDC） |
| 入出庫予定 | 品目コード, 拠点コード, 予定数量, 予定日, 種別（入庫/出庫） | 日次（差分） |
| 拠点マスタ | 拠点コード, 拠点名, 拠点区分（工場/倉庫/DC）, 住所, 親拠点コード | 週次（全量） |
| ロケーションマスタ | ロケーションコード, 拠点コード, 保管区分, 最大容量 | 週次（全量） |

### 連携方式

```
WMS（Oracle WMS / Blue Yonder）
  │
  ├─ CDC（LogMiner）  ──→ Kafka Topic: sc.inventory.stock-movement
  │    └─ 在庫移動トランザクション
  │
  └─ バッチ抽出（API / DB）  ──→ Data Lake: /raw/inventory/
       └─ スナップショット、マスタデータ
```

### 技術仕様

- **CDC方式:** Oracle LogMiner → Debezium → Kafka
- **バッチ方式:** WMS REST API → Python抽出スクリプト → ADLS Gen2
- **データ形式:** CDC=Avro、バッチ=Parquet（Snappy圧縮）
- **パーティション:** 拠点コード × 日付でパーティション

### SLA

| 指標 | 目標値 |
|---|---|
| 在庫移動CDC遅延 | ≦3分 |
| 日次スナップショット完了時刻 | 翌営業日 06:00 JST |
| データ可用性 | 99.5%/月 |

## 4. 物流系統（TMS連携）

### 対象システム
- **ソースシステム:** 輸送管理システム（TMS）/ 外部物流会社API
- **ターゲット:** 統合データレイク（物流レイヤー）

### 連携データ

| データ種別 | 主要フィールド | 連携頻度 |
|---|---|---|
| 出荷指示 | 出荷番号, 品目コード, 出荷数量, 出荷元/先拠点, 要求納期, 輸送手段区分 | リアルタイム（CDC） |
| 輸送実績 | 出荷番号, 実出発日時, 実到着日時, 輸送会社コード, 車両/フライト番号, 状態（積載/輸送中/着荷）| リアルタイム（Webhook） |
| 輸送車両トラッキング | 車両ID, GPS座標, 速度, タイムスタンプ | リアルタイム（IoT、30秒間隔） |
| 輸送ルートマスタ | レーンID, 出発拠点, 到着拠点, 輸送手段, 標準リードタイム, 距離 | 週次（全量） |
| 輸送会社マスタ | 輸送会社コード, 名称, 対応輸送手段, 評価スコア | 月次（全量） |
| 外部データ（気象・港湾） | 地点, 気象状態, 港湾混雑インデックス, タイムスタンプ | リアルタイム（外部API） |

### 連携方式

```
TMS（SAP TM / JDA TMS）
  │
  ├─ Webhook（HTTP POST）  ──→ API Gateway  ──→ Kafka Topic: sc.logistics.shipment-status
  │    └─ 輸送状態更新イベント
  │
  └─ バッチ（REST API）  ──→ Data Lake: /raw/logistics/

外部物流API（GPS/気象/港湾）
  └─ REST API ポーリング  ──→ Kafka Topic: sc.logistics.tracking
```

### 技術仕様

- **Webhook処理:** Azure API Management → Event Hub → Kafka
- **外部API連携:** Python Airflow DAG（ポーリング）→ ADLS Gen2
- **GPS/テレメトリ:** Azure IoT Hub → Stream Analytics → Kafka
- **データ形式:** イベント=JSON（スキーマバリデーション必須）、バッチ=Parquet

### SLA

| 指標 | 目標値 |
|---|---|
| 輸送状態更新遅延 | ≦5分 |
| GPSトラッキング遅延 | ≦1分 |
| バッチ処理完了時刻 | 翌営業日 07:00 JST |
| データ可用性 | 99.5%/月 |

## 5. 品質系統（品質システム連携）

### 対象システム
- **ソースシステム:** 品質管理システム（QMS）/ 検査機器API / 顧客クレームDB
- **ターゲット:** 統合データレイク（品質レイヤー）

### 連携データ

| データ種別 | 主要フィールド | 連携頻度 |
|---|---|---|
| 受入検査実績 | 検査番号, 品目コード, ロット番号, 検査日時, 合否区分, 不良コード, 不良数量 | リアルタイム（CDC） |
| 工程内検査実績 | 検査番号, WO番号, 工程コード, 検査項目, 実測値, 合否区分, 検査日時 | リアルタイム（CDC） |
| クレーム（市場不具合） | クレーム番号, 車台番号, 品目コード, 不具合内容, 発生日, 対応ステータス | 日次（差分） |
| 不良コードマスタ | 不良コード, 不良名称, 不良区分（機能/外観/寸法）, 重要度 | 月次（全量） |
| SPC（統計的工程管理）データ | 計測点ID, 工程コード, 計測値, 管理限界（UCL/LCL）, タイムスタンプ | リアルタイム（IoT） |

### 連携方式

```
品質システム（SAP QM / Siemens Opcenter Quality）
  │
  ├─ CDC（DBログ）  ──→ Kafka Topic: sc.quality.inspection-result
  │    └─ 検査実績
  │
  ├─ OPC-UA / REST API  ──→ Kafka Topic: sc.quality.spc-data
  │    └─ 検査機器SPC計測
  │
  └─ バッチ（REST API）  ──→ Data Lake: /raw/quality/
       └─ クレーム, マスタ
```

### 技術仕様

- **CDC方式:** Debezium（PostgreSQL/MSSQL対応）→ Kafka
- **検査機器:** OPC-UA Server → Azure IoT Hub → Kafka
- **データ形式:** SPC=JSON（時系列）、検査実績=Avro、バッチ=Parquet
- **個人情報保護:** クレームデータは個人識別情報をマスキング処理後に格納

### SLA

| 指標 | 目標値 |
|---|---|
| 検査実績CDC遅延 | ≦3分 |
| SPC計測データ遅延 | ≦1分 |
| クレームデータ反映 | 当日 23:00 JST |
| データ可用性 | 99.5%/月 |
